## Confirmed release blockers

### RR-001: session lock does not invalidate an in-flight authenticated refresh

**Affected component:** background session lifecycle and PR refresh.

**Evidence:**

- `src/background/prManager.ts:176` decrypts the PAT into the local `token`
  variable. `src/background/prManager.ts:185` and the calls beginning at
  `src/background/prManager.ts:230` can then continue the `/user`, search,
  detail, review, and CI requests using that local token.
- `entrypoints/background.ts:211-223` handles `CLEAR_SESSION` by clearing
  `state.sessionPassword`, remembered-session storage, and alarms. It neither
  aborts nor invalidates `inFlightRefresh`.
- `src/background/prManager.ts:255` and `:349` can perform successful-refresh
  persistence after awaits. Depending on exactly when sign-out occurs, later
  persistence may fail because the shared password is now null, or it may
  complete with a password already captured by a queued operation. Neither
  outcome stops the already-authenticated GitHub requests.
- The existing sign-out E2E test covers an idle sign-out, not a periodic alarm
  refresh paused after PAT decryption.

**Deterministic reproduction design:**

1. Establish an authenticated remembered session.
2. Start an automatic refresh and pause the mocked `/user` or first search
   response after `decryptToken` has returned.
3. send `CLEAR_SESSION` and await the response; verify the popup is locked and
   session storage is empty.
4. release the mocked response.
5. Observe that subsequent GitHub requests are still issued with the PAT held
   by the refresh operation; depending on the pause point, badge/storage or
   notification side effects may also finish after lock.

This path is reachable when the five-minute alarm starts while an already-open
dashboard still exposes the Sign Out control. Manual refresh loading hides that
control, but the periodic refresh does not.

**Observed behavior:** session state and UI lock immediately, while the
previously started operation remains authoritative and can continue using the
decrypted PAT.

**Expected behavior:** once explicit sign-out succeeds, no background operation
may continue authenticated work or commit authenticated results under the old
session. The encrypted PAT must remain stored for password-based sign-in.

**Impact:** a user who explicitly locks the extension has a bounded but real
window in which GitHub access and possibly extension side effects continue.
This violates the specified security/session contract; it is not an argument
for deleting the encrypted PAT.

**Recommended isolated follow-up PR:** `fix/invalidate-refresh-on-session-lock`.
Introduce a background-owned session generation or cancellation signal,
capture it when a refresh starts, and invalidate/abort the active operation on
`CLEAR_SESSION`. Re-check session validity before post-fetch side effects. Make
`CLEAR_SESSION` await session-storage/alarm cleanup before responding. Add a
deferred-request regression proving sign-out prevents later GitHub requests and
snapshot/badge/notification commits, while ordinary sign-out still preserves
the encrypted PAT and password-only sign-in.

## Authentication and session audit

### Initial setup and unlock

- A new token remains on the token-entry screen after token-validation failure.
  Token encryption and password setup do not begin until validation succeeds.
- Existing-user unlock validates the password against the AES-GCM test vector
  before sending `SET_PASSWORD`; an incorrect password remains on the unlock
  screen.
- The popup changes to `authenticated` before the initial/background
  `CHECK_PRS` response is inspected. This is appropriate for GitHub refresh
  failures because authentication and access to cached encrypted data have
  already succeeded. However, the boolean responses from `SET_PASSWORD` and
  `CHECK_PRS` are not checked in `useAuth`; rejected messages are caught, but a
  resolved `false` response is ignored. No normal valid-input path currently
  returns `false`, so this is recorded as robustness debt rather than a
  release blocker.
- Remembered-session initialization trusts the password returned by the
  background and does not re-run the test-vector validation. That value is
  sourced only from extension session storage written after a validated setup
  or unlock. Malformed storage shapes are rejected by `SessionStorageSchema`.

One low-probability setup failure is described under deferrable issue D-004.

### Token-validation errors

PR #66 remains correct:

| Condition                                      | Current result                                                                                                  |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| HTTP 401                                       | “Invalid GitHub token”; token retained; remains on login screen.                                                |
| Recognized 403/429 rate limit                  | Temporary rate-limit message, formatted deadline when available, persisted cooldown, no authentication advance. |
| Ordinary 403                                   | Required-permissions message, distinct from invalid credentials.                                                |
| HTTP 5xx                                       | Temporary GitHub-unavailable message.                                                                           |
| Network rejection                              | Connectivity message without raw exception text.                                                                |
| Successful response without exact `repo` scope | Scope-specific error and no authentication advance.                                                             |

Unit tests cover all of these classifications, and packaged E2E covers 401,
missing scope, and a controlled 429 while retaining token input.

### Password and authentication copy

The login and unlock screens correctly distinguish the PAT from the local
password. Ordinary sign-out does not say that the PAT was deleted, and the
unlock screen asks for the password rather than the PAT.

The password-setup screen contains two inaccurate statements:

- “You'll need this password each time you open PR Tracker” conflicts with the
  optional remembered session.
- “Your password is never stored anywhere” conflicts with plaintext password
  storage in the in-memory `browser.storage.session` area when the user selects
  “Remember password for 12 hours.” Chrome documents that this area is
  in-memory, trusted-context-only by default, and cleared on browser restart,
  extension reload/update, disable, or uninstall ([Chrome storage
  documentation](https://developer.chrome.com/docs/extensions/reference/api/storage#property-session)).

Proposed copy, without changing the model:

> Create a password to encrypt your GitHub token and locally stored PR data.
> You will use this password to unlock PR Tracker after signing out or when a
> remembered session is unavailable.

> Your password is not written to persistent local storage. If you choose
> “Remember password,” it is kept in the browser's in-memory extension session
> for up to 12 hours and is cleared on sign-out or browser restart.

The reset confirmation accurately says the encrypted PAT will be removed, but
its broader “all stored data” claim does not match the current reset scope; see
product decision P-004.

### Sign-out and sign-in

Verified idle behavior:

- `CLEAR_SESSION` clears the process-local password and remembered flag,
  removes the session-storage password/flag, and clears password-expiry and
  periodic-refresh alarms.
- The popup clears its token, password, and confirmation state and renders the
  password-entry screen.
- The encrypted PAT, encryption metadata, encrypted PR/app data, and preferences
  remain in local storage.
- The locked popup does not render the PR dashboard. `usePullRequests` retains
  its React PR array until the popup closes, but the array is not rendered or
  reloaded while authentication state is locked.
- Subsequent password validation restores the session and dashboard without a
  new PAT. Packaged E2E verifies this complete journey.

RR-001 is the exception for already-running work. Also, `CLEAR_SESSION` sends
its success response without awaiting the asynchronous storage/alarm removals.
The current E2E observes them cleared, but the follow-up should make completion
part of the message contract.

### Remembered sessions

| Lifecycle event                   | Current behavior                                                           |
| --------------------------------- | -------------------------------------------------------------------------- |
| Popup close/reopen                | Restored from `browser.storage.session`; E2E verified.                     |
| Popup reload                      | Restored; E2E verified.                                                    |
| Chrome MV3 service-worker restart | Background startup reloads validated session storage; unit verified.       |
| Browser restart                   | Session storage is cleared by the browser, so password unlock is required. |
| 12-hour expiry alarm              | Password/flag are removed and process-local session is cleared.            |
| Explicit sign-out                 | Password/flag and alarms are removed; idle sign-out is not auto-restored.  |

The “12 hours” option is therefore an upper bound, not persistence across a
browser restart. This is compatible with the stated model and improves the
lock boundary.

## GitHub API and refresh reliability

### Verified behavior

- Search state is local UI state and survives storage-driven data refreshes.
- Search-page HTTP/network/JSON/schema errors and `incomplete_results` return a
  complete-refresh failure. The manager preserves cached PRs, badge,
  timestamps, comparison state, and emits no `DATA_UPDATED` storage signal.
- Every canonical PR detail is required. A missing URL, non-success response,
  invalid JSON, or unusable identity fails the refresh rather than filtering a
  PR out. Review/check/combined-status failures remain optional and become
  `pending`.
- `checkPullRequests` returns the same in-flight promise to overlapping manual
  and automatic callers, and reliably clears that state after success or
  failure.
- Encrypted application-data changes use one background mutation queue. Each
  queued mutation decrypts the latest committed value, and queue cleanup runs
  after both success and rejection.
- Authored/review search overlaps are deduplicated by canonical PR API URL
  before detail work. Each unique PR makes one canonical detail request and
  reuses its repo/SHA for optional review and CI requests.
- Pagination uses 100-result pages, validates the first page's count, stops
  without an extra request when the target is reached, and caps each query at
  1,000 results/10 pages.
- The promise pool owns the complete detail/review/CI unit and limits active PR
  units to four. Ordinary required failures finish bounded work; a recognized
  required-detail rate limit stops queued units while already-active units
  settle.
- Required `/user`, search, and detail rate limits preserve cached state and
  persist a cooldown. Automatic work is silent during cooldown; manual work
  reports the deadline. Expiry clears the cooldown and allows recovery.
- Optional review/check/status rate limits retain `pending`, finish all PR
  identity work, persist the complete snapshot plus the latest cooldown, and
  suppress the next refresh.
- Popup manual refresh/query operations use structured `finally` cleanup and
  check the background boolean response. Runtime-message rejection produces a
  controlled popup error; the former 1.5-second delay is absent.
- Encrypted app-data storage changes are authoritative for popup reloads.
  `DATA_UPDATED` is semantic only. Reload coalescing permits one serial trailing
  pass, so a later real commit is not lost.

### Cross-mechanism interaction: default search peers

The default authored and review-requested searches are launched together with
`Promise.all` at `src/background/api.ts:536-539`. Each peer paginates
independently, and there is no shared `AbortController` or stop signal. If one
peer receives a recognized rate limit, the other continues until it succeeds
or fails, potentially making up to its remaining 10 search-page requests. Only
after both settle does the caller select the rate-limited failure and persist
the cooldown.

Impact: cached-data safety is preserved and no detail work starts, but cooldown
persistence can be delayed and the successful peer may consume additional
search quota during a secondary-limit event. This is verified deferrable issue
D-001, not a data-integrity blocker.

## Security and privacy review

### Cryptography and local state

- PAT, app data, preferences, comparison snapshot, and hidden IDs use AES-GCM
  with fresh 12-byte IVs.
- Keys are derived with PBKDF2-SHA-256, a random 16-byte salt, 100,000
  iterations, and the public extension ID plus user password. The extension ID
  is binding/context, not additional secret entropy.
- Minimum password length is eight characters. A copied browser profile permits
  an offline password-guessing attack against the stored test vector; security
  depends materially on password strength and the fixed PBKDF2 work factor.
  No migration or immediate release blocker is asserted, but the work factor
  should be reviewed separately against the project's intended threat model.
- The popup holds the entered PAT in React state after setup until popup close
  or sign-out. The background holds the decrypted PAT only in local refresh
  variables. Passwords are held in popup/background memory and, when opted in,
  plaintext in browser session storage for up to 12 hours.
- Encrypted PR data can remain in popup React state after sign-out, but the
  locked render path does not expose the dashboard. Closing the popup destroys
  that context. RR-001 covers the separate background-operation problem.

### Messages, logs, network, and notifications

- Passwords cross only extension-internal runtime messages. There is no
  `externally_connectable` declaration and no content script in the product.
- Production logs contain lifecycle/status text and notification titles, not
  PATs or passwords. Fetch errors may include endpoint context but Authorization
  headers are not logged.
- Runtime API requests go to `api.github.com`; PR/author/reviewer avatar image
  URLs supplied by GitHub can also be loaded by the popup. There is no PR
  Tracker backend or analytics request.
- Desktop new-PR notifications expose only a count. Error notifications expose
  operational messages, not repository names, PR titles, PATs, or passwords.

### Permissions and artifacts

- Production manifests contain only `storage`, `notifications`, and `alarms`,
  plus GitHub API host access. No permission changed since v1.0.19.
- Chrome and Firefox output contains zero matches for
  `TEST_RESET_BACKGROUND_STATE`, either test reset helper name, fixture token
  prefixes, `GITHUB_TOKEN`, or `TEST_PASSWORD`.
- PR #71's reset handler is compiled only in Vite `test` mode and its reset
  refuses an active refresh instead of cancelling production work.
- No `.env` file, live credential, encryption key, or sanitized fixture secret
  is present in the production output inventory.

The public privacy policy says the extension does not transmit data to external
servers while also acknowledging direct GitHub API communication, and says
Reset App clears all stored data. Those statements should be reconciled with
the actual GitHub transmission, remembered-session option, and reset matrix in
a focused copy/privacy review (D-002/P-004).

## Deferrable issues

### D-001: rate-limited default search does not stop its peer

The peer can make additional search calls and delay cooldown persistence, but
the refresh remains failed and cached state is preserved. A future API-focused
PR can share an abort/stop signal between the two default search paginators and
test both peer orderings. Do not combine this with RR-001 unless the same
cancellation abstraction can remain clearly scoped.

### D-002: authentication and privacy copy overstates storage behavior

The “never stored anywhere” and “each time you open” password statements are
factually inaccurate when remembering is enabled. The privacy policy also uses
overbroad “no external servers” and “all stored data” language. This does not
expose credentials by itself, but it weakens informed consent around the
password security boundary. Use the replacement setup copy above and align the
privacy/reset text after P-004 is decided.

### D-003: `CLEAR_SESSION` does not await storage/alarm cleanup

Idle E2E passes, but the message returns before the asynchronous removals
settle. Fold this into the RR-001 follow-up so successful sign-out means both
session invalidation and durable cleanup have completed.

### D-004: encryption test-vector setup failure is swallowed

`setupEncryption` returns `false` after catching its own error, while
`encryptToken` at `src/services/secureStorage.ts:368` ignores that result. A
token write can therefore be reported as successful without the test vector
needed for later password unlock. This requires an unusual second-step crypto
or storage failure after token encryption succeeds, so it is not the primary
release blocker. A focused secure-storage PR should propagate failure and make
initial setup atomic or safely recoverable.

### D-005: comparison snapshot remains a second fallible write

Normal successful and notification-suppressed paths are correct, but a failure
of the second `oldPullRequests` write is logged and swallowed after current PR
data was already committed. A future persistence PR can evaluate committing
current and comparison state in one serialized mutation without changing when
comparisons observe the prior snapshot.

### D-006: Firefox runtime coverage is build-only

No current regression indicates a Firefox failure, and the MV2 build succeeds.
The lack of packaged Firefox runtime automation remains a coverage limitation,
not a confirmed defect.

### D-007: release workflow and repository metadata debt

The root manifest is stale/non-authoritative, CI does not run compile, lint,
format, or dependency audit, and publish actions use moving version tags rather
than immutable commit SHAs. These are operational/supply-chain hardening items
that should be handled separately from v1.0.20 runtime fixes.

## Product decisions requiring maintainer input

### P-001: replay after notifications are re-enabled

**Existing implementation:** successful refreshes advance
`oldPullRequests` even when notification preference disables delivery.

**Consequence:** PRs discovered while disabled are never replayed after the
preference is enabled.

**Options:** retain no-replay semantics; retain a separate acknowledged-ID
model; or introduce a notification queue. The latter two add state/migration
complexity and are explicitly outside the current architecture.

**Compatibility:** keeping current behavior requires no migration. Changing it
requires defining upgrade behavior for already advanced snapshots.

### P-002: hidden PR notification eligibility

**Existing implementation:** hidden IDs affect display after new-ID comparison;
hidden PRs remain notification-eligible and count in the grouped message.

**Consequence:** a user can hide a PR but still receive a later grouped “new PR”
count that includes it if it is new to the comparison snapshot.

**Options:** keep notification identity independent of visibility; exclude
currently hidden IDs from delivery only while still advancing the snapshot; or
define a separate muted state.

**Compatibility:** delivery-only exclusion requires no stored-data migration.
A separate muted state would require schema and UX work.

### P-003: meaning of “Most Urgent”

**Existing implementation:** more requested reviewers sorts first.

**Consequence:** the label may imply age, failing CI, requested action, or review
state even though none participates.

**Options:** rename it to “Most Reviewers”; document reviewer count as the
urgency proxy; or define and test a broader urgency score.

**Compatibility:** renaming is copy-only. Changing ordering affects saved
`urgent` preferences but does not require storage migration if the enum remains.

### P-004: full-reset retention scope

**Existing implementation:** reset deletes credentials, key material, encrypted
app/preferences/snapshots, and session state, but retains theme, hidden-ID
ciphertext, cooldown metadata, first-run flag, and process-local throttles.

**Consequence:** the user-facing “all stored data” promise is false; a newly
configured account can inherit theme or a temporary cooldown. Hidden ciphertext
is no longer decryptable after salt deletion.

**Options:** make Reset App clear all extension local/session state and known
process-local state; or preserve selected non-sensitive preferences and state
that precise scope in UI/privacy copy.

**Compatibility:** clearing everything changes reset behavior but needs no data
migration. Selective retention needs an explicit stable list and tests.

### Decisions already established and not reopened

- Sign-out is a lock and retains the encrypted PAT.
- Password-only sign-in after ordinary sign-out is required.
- Remembered sessions are opt-in and must be cleared by explicit sign-out.
- First-run notifications default off.
- New PRs are grouped into one count notification.
- Selected authentication/session errors may bypass the ordinary notification
  preference.
- Review classification uses each reviewer's latest state with
  `CHANGES_REQUESTED` precedence.

## Verified behaviors requiring no release work

- Initial 401, rate-limit, ordinary 403, server, and network failures do not
  advance token-entry authentication state.
- Ordinary idle sign-out locks the popup, clears active/remembered session
  state, preserves the encrypted PAT, and supports password-only sign-in.
- Popup search state, filtering, and preference state survive legitimate data
  updates.
- Failed search/detail and cooldown-suppressed refreshes preserve last-known
  good PR and comparison data.
- Complete successful refreshes advance current and comparison snapshots when
  notification display is enabled, disabled, throttled, or rejected.
- Overlapping refreshes and app-data writes remain serialized.
- Pagination, deduplication, concurrency bounding, rate-limit persistence,
  expiry, and recovery match their documented contracts.
- Popup refresh/query loading has no fixed wait and cannot remain loading after
  a handled runtime-message failure.
- Unit tests are browser-free. E2E owns and closes its browsers and detaches
  GitHub mock handlers.
- Test-only E2E reset code is absent from both normal production builds.
- Production builds contain no detected fixture credentials or environment
  secret names.

## Release-readiness conclusion

**Not yet ready.** RR-001 is a confirmed conflict with the decided lock-session
security contract: an already-running refresh is not invalidated by explicit
sign-out and can continue using its decrypted PAT. The next implementation PR
should address only session invalidation/cancellation and awaited sign-out
cleanup while preserving the encrypted PAT and password-based unlock model.

After that fix, the maintainer should explicitly resolve or accept the listed
notification/reset product policies, rerun the unavailable dependency audit,
and then create a separate v1.0.20 release-preparation PR. This audit does not
authorize publication.
